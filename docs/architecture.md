# Architecture

The native Python process is the Raspberry Pi application. React/Express is an independent browser demo; it does not orchestrate the Python drivers.

```text
Camera motion -> state machine -> microphone capture -> Whisper transcript
                                      |
                                      v
                        Gemini text or local llama.cpp
                                      |
                             bounded clause queue
                                      |
                      Piper synthesis (one loaded voice)
                                      |
                            bounded prepared WAV queue
                                      |
                  one playback channel + timed mouth animation
                                      |
                              resume listening
```

## State and concurrency

`main.py` processes pygame events, camera observations, and queued worker results on the display thread. The lifecycle is `IDLE -> WAKE_PENDING -> GREETING -> LISTENING -> THINKING -> SPEAKING -> LISTENING`, with `COOLDOWN` after repeated silence or a failed turn. A manually submitted question may start from IDLE or COOLDOWN.

Only one microphone worker is admitted at a time. Results carry a turn identifier, so audio captured before an injected question cannot later become a new response. Workers report completion through an event queue; they do not perform state transitions. Duration/deadline measurements use monotonic clocks.

`speech_pipeline.py` separates generation, synthesis, and playback with two bounded queues. There is one synthesizer worker, preventing concurrent model use and unbounded CPU/memory consumption. The playback stage disposes of per-phrase WAV files on success, failure, and cancellation. Late synthesis results are also disposed of. A partial response is retained rather than regenerated by a second model after a connection failure. Synthesis/playback errors do not trigger a model retry.

The persistent Piper Python runtime avoids loading ONNX for every clause. Its optional CLI fallback has a timeout; the cache is bounded and keyed by text, voice files, and voice settings. Startup warms the greeting off the display thread. Production does not silently substitute synthetic tones unless explicitly configured.

## Model routes

`conversation_mode: auto` prefers Gemini if configured and below the application token limits. `local` always uses llama.cpp. The `gemini_live` mode also permits local fallback on cloud failure.

The default cloud path uses `generate_content_stream`, bounded history, and the same clause/Piper pipeline as the local model. Local streaming uses a pooled HTTP session and prompt caching where supported by llama.cpp. Cloud failures enter a short retry cooldown to avoid repeatedly delaying the next turn.

Optional `response_voice: native` sends the completed Whisper transcript and recent history to Gemini Live, receives 24 kHz PCM plus output transcription, and queues audio on one pygame channel. Receive and playback run separately; playback drains before the microphone reopens. Native voice is Charon. This is a turn-based interaction, not a continuously open duplex microphone stream. It does not implement conversational interruption/echo cancellation.

`TokenSafeguard` stores reported usage atomically in `hardware.cache_dir`, resets daily totals at UTC midnight, and resets visitor totals on cooldown/idle. Streaming cumulative snapshots are recorded once per request. These are best-effort admission checks, not strict billing enforcement: in-flight responses and missing usage metadata can exceed or undercount limits. Run one app instance per cache file.

## Input and graphics

Whisper runs on CPU with int8 and a bounded thread count. Microphone calibration runs once. Both PortAudio and arecord use configurable silence endpointing. Arecord keeps a short pre-roll and the speech interval in memory, starting its maximum phrase duration when speech begins. A failed/empty local transcript does not silently invoke a cloud recognizer by default.

The camera supports Picamera2 and OpenCV. CPU motion detection is throttled and downsampled, with normalized gaze estimates from motion regions. Hailo SDK presence is diagnostic only; HEF loading and accelerator inference are not implemented. The renderer uses cached, immutable small camera previews when enabled.

Pygame uses matching full portrait images, amplitude-derived mouth poses, blinks, subtle drift, and small cached particle sprites. Mouth poses are approximate audio analysis, not a phoneme recognizer. Captions wrap inside the frame. Native rendering defaults to 30 FPS; browser rendering is also capped at 30 FPS. Diagnostic HUD and camera overlay start hidden.

## Deployment limits

Automated checks cover lifecycle races, partial failures, SDK serialization with mocked HTTP, PCM ordering/draining, cache/resource cleanup, and rendered surfaces. Real Raspberry Pi camera/audio devices, Hailo hardware, a running local model, cloud credentials, and live voice quality still require deployment testing. Use the HUD's transcript-to-playback turnaround and `tools/benchmark_renderer.py` to measure the actual installation.
